# 日常本 DailyBook v1.9

**记账 + 生活 + 学习 + 待办 + 专注计时** 五合一安卓应用。
Kotlin + Jetpack Compose + Room，纯离线，只申请通知、震动与开机重排提醒三个权限。
界面支持简体中文 / 繁體中文 / English / 日本語 四种语言，应用内切换、立即生效。

## 设计要点

- **单一数据源**：专注统计（今日/连续/累计、本周/本月、热力图）全部从 `focus_sessions` 表实时派生，
  不再另存一份计数；v1.7 的看板分组、环比对比、智能洞察与月报同样是从这一份 UiState 现场派生的，
  不另存快照；v1.8 的桌面小组件也不另存一份统计——它每次刷新直接查三张表当天/未完成的行现算；
  v1.9 的两个新模块也一样：习惯的「连续 N 天」、本周天数与 7 天小格全部从 `habit_logs` 现场算，
  GPA、学分进度、学习周报与倒计时小组件都是从同一份 UiState / 那几张表现算，没有任何缓存计数；
  主题/界面语言/配色方案/月度预算/分类预算/自定义分类/币种汇率/专注目标/学习设置/背景图只有一份全局单例设置。
- **界面语言（i18n）**：四种语言在 `i18n/Lang.kt` 里是一个枚举，取值一律走
  `pick(lang, zhCn, zhTw, en, ja)`——四个槽位必须在编译期全部给出，**漏翻一种语言是编译错误**，
  而不是运行期冒出一个空串或悄悄回落。这是整套方案唯一的强制手段，也是最有效的一条：
  加新文案时编译器会直接逼你把四种语言补齐，不靠人盯。带参数的文案走 `pickf()`，
  内部用 `Locale.ROOT` 格式化，免得小数点被本地化成逗号。
  语言存在设置里（`SettingsStore.lang`），由 `MainActivity` 通过 `LocalLang` 这个 CompositionLocal 往下传，
  所以一切换整棵 Compose 树重组、**立即生效不用重启**；屏幕、通知、CSV 表头、日期与截止日/月份标签
  全都按同一个 `lang` 取值（`TimerViewModel`、`Notifier`、`SummaryReceiver` 这些非 Composable 的地方
  直接读 `SettingsStore.lang.value`）。语言是**应用内设置**、不跟随系统，只有启动器名称和长按快捷方式
  的标签例外——那是系统 UI，走 `res/values/`、`res/values-zh-rCN/`、`res/values-zh-rTW/`、`res/values-ja/`
  里的 `@string`，跟随系统语言。
  **v1.9 的两个新文案表也走同一条路**（`LifeStrings` 84 个函数、`StudyStrings` 206 个函数），
  并且都登记进 `I18nSmokeTest` 那张表里让反射真跑一遍，所以「漏参数」这类崩溃不会被新模块带进来。
- **小路由器（v1.9）**：这一版页面一下子多了十几个（5 个标签 + 生活 5 页 + 学习 8 页 + 设置 7 个分类页 +
  关于 + 检查更新 + 统计 5 个详情页），但**依然没有引入 navigation 库**：`ui/Nav.kt` 里
  `Route` 是一个 `sealed interface`（`data object` / `data class` 带参数），页面栈就是
  `MutableList<Route>`，`Navigator` 只有 `push()` / `pop()` / `popToTop()` 三个方法，
  返回交给 `MainActivity` 里一个 `BackHandler(enabled = stack.isNotEmpty())`。
  这么做是有意的：库能省的那点样板代码，代价是一个新依赖 + 一套必须学的概念（back stack owner、
  deep link、参数序列化），而这里所有页面都在同一个 Activity、同一个 ViewModel 之下，
  `Sealed interface` 的 `when` 已经是穷尽的编译期检查——加一个 Route 忘了接页面会直接编译报错，
  比运行期点进去白屏强。侧边导航栏与底部标签条共用同一份 `Tab` 枚举，所以宽屏和窄屏不会走岔。
- **设置的七分类拆分（v1.9）**：原来的 `ui/SettingsScreen.kt` 是一整页长列表（三四十个开关堆在一起），
  这版把它**删掉**、拆成 `ui/settings/` 四个文件：`SettingsHomeScreen` 只列七个分类，
  `SettingsCategoryScreen` 按 `SettingsCategory` 枚举渲染对应的一组设置项。
  拆分刻意做到**只搬不改**：每一项的行为、默认值、文案键都没动，改的只是它出现在哪个分类下，
  所以「设置找不到了」的抱怨可以靠分类名解决，而不会引入一批新 bug。
  顺带删掉了页脚那段「v1.4 新特性」的说明文字（用户明确要求去掉），
  新增的只有「学习」分类三项与「关于 / 检查更新」两页。
- **关于与检查更新（v1.9）**：这一页是**诚实设计**的样本。版本号不写死，`rememberAppVersion()`
  在运行时从 `PackageManager` 读 `versionName` / `longVersionCode`（关于页与检查更新页共用同一份，
  所以两处永远不会打架），最低 Android 版本也从 `Build.VERSION_CODES` 那一侧说明。
  「检查更新」本可以做一个假的进度条然后说「已是最新」，但**这个应用没有 `INTERNET` 权限**，
  真的去查版本号就得加权限——那是这次改造明确不要的。所以这一页只做两件事：
  显示你当前装的是哪个版本，以及用 `ACTION_VIEW` 把 GitHub releases 页交给浏览器
  （`startActivity` 包在 `runCatching` 里，设备上没有浏览器时只弹一句 Toast，不崩），
  页面上明写「应用没有联网权限，所以查不了」，把判断交给用户自己。
- **多账户**：交易表的 `account` 列存账户名（字符串，不建外键也不建单独的表，方便用户随手加一个）。
  `Accounts.PRESETS` 是「现金 / 微信 / 支付宝 / 银行卡 / 其他」五个预置项，记录弹窗在此基础上把
  「历史用过的账户 ∪ 当前值」并进去，所以自己输入过的账户下次直接能点。
  现金是默认账户（`Accounts.DEFAULT`），列表里只在账户不是现金时才显示徽标；
  顶部筛选胶囊只有在历史数据里出现过 2 个以上账户时才显示，避免单账户用户看到无用控件。
- **分类预算**：分类上限存在设置里（`Map<分类, 分>`），和整月预算并存、互不干扰——
  月预算管「这个月总共花多少」，分类预算管「这个分类这个月花多少」。
  统计页把当月支出按分类聚合后算出进度与是否超支，超支的进度条走红色；
  分类预算只对支出分类有意义，收入不受影响。
- **预算预警**：记完一笔（`MainViewModel.checkBudgetAlert()`）后重算一遍当月支出，命中三种情况各推一条通知：
  月度预算用到 80%、月度预算超支、某个分类预算超支。去重键是「月份 + 阈值」
  （`2026-05:near` / `2026-05:over` / `2026-05:cat:餐饮`），所以**同一个月里同一个阈值只打扰一次**，
  换月后键变了会自动重新计；总开关在设置里（`budgetAlert`），关掉就整段不检查。
- **数据库迁移**：v1→v2 用 `Migration` 新增 `focus_sessions` 表；v2→v3 用
  `ALTER TABLE todos ADD COLUMN repeatRule TEXT NOT NULL DEFAULT 'NONE'` 补上重复规则列；
  v3→v4 再用 `ALTER TABLE transactions ADD COLUMN account TEXT NOT NULL DEFAULT '现金'` 补上账户列；
  v4→v5（`MIGRATION_4_5`）用七条 `ALTER TABLE ... ADD COLUMN` 给 `transactions` 补上
  `tags` / `reimbursable` / `reimbursed` / `currency` / `foreignAmountCents` / `rateScaled`，
  给 `focus_sessions` 补上 `interrupted`，每条都带 NOT NULL 默认值
  （空标签、0=不待报销、0=未报销、`'CNY'`、0、10000、0=未中断）。
  v5→v6（`MIGRATION_5_6`）给 `todos` 补两列——`priority TEXT NOT NULL DEFAULT 'NORMAL'`
  与 `sortOrder INTEGER NOT NULL DEFAULT 0`，并新建两张表：`subtasks`
  （id / todoId / title / done / sortOrder / createdAt）和 `recurring_tx`
  （id / amountCents / typeName / category / account / note / tags / rule / nextDueMillis / enabled / createdAt），
  两张新表都用 `CREATE TABLE IF NOT EXISTS`，所以重复执行也不会炸。
  **v6→v7（`MIGRATION_6_7`，v1.9）**：给 `todos` 补一列
  `courseName TEXT NOT NULL DEFAULT ''`（空表示这条待办不属于任何课程，所以老数据显示为空串 → 不进「作业」），
  再用 `CREATE TABLE IF NOT EXISTS` 新建 11 张表：`memos` / `milestones` / `important_dates` /
  `habits` / `habit_logs` / `courses` / `exams` / `study_tasks` / `grades` / `credit_targets` / `awards`。
  **这次迁移是按 Room 自己生成的 DDL 逐列对过的**：把 `AppDatabase_Impl.java` 里每张表的建表语句
  与手写的迁移 SQL 放在一起比列名 / 类型 / 非空 / 默认值，再用真实 SQLite 造一个 v6 老库跑一遍迁移，
  确认结构一致且老数据不丢（脚本在工作区根目录的 `verify-migration-v19.js`）。
  之所以这么小心：Room 的 `identityHash` 一旦与迁移结果对不上，用户升级时会直接崩在打开数据库那一步，
  而这是发布后才最容易炸、也最难查的一类问题。
  六次迁移都在 `addMigrations(...)` 里注册，老用户的记账、待办、专注记录完整保留；
  加了默认值之后，老数据自动落在安全取值上：无标签、不是待报销、人民币且汇率 10000、
  待办优先级是「普通」（`NORMAL`）、手动顺序 0、没有子任务、没有课程名，生活与学习那几张新表就是空的。
- **备份与恢复**：整库导出成一个 JSON 文件（记账流水 / 待办 / 子任务 / 周期记账规则 / 专注记录 +
  月度预算 + 分类预算 + **v1.9 的生活几段（备忘录 / 大事记 / 重要日期 / 习惯与打卡）与学习几段
  （课程 / 考试与复习任务 / 成绩 / 学分目标 / 奖助）**，带 `app` 与 `format` 版本字段，
  **当前 `format = 5`**；v1.4 起记账多了 `account`、
  待办多了 `repeatRule`，v1.6 起记账再多了 `tags` / `reimbursable` / `reimbursed` / `currency` /
  `foreignAmountCents` / `rateScaled`，专注记录多了 `interrupted`，v1.7 起待办再多了 `priority` /
  `sortOrder`，并多了 `subtasks` 与 `recurring` 两段，**v1.9 起待办再多了 `courseName`，并多了上面那九段；
  解析时校验并拒绝不认识的结构**）。
  `format` 比当前新会直接拒绝，比当前旧则逐字段回退到默认值（账户回退成「现金」、
  重复规则回退成 `NONE`、标签为空、不是待报销、币种回退成 CNY 且汇率 10000、
  专注记录回退成未中断、待办优先级回退成 `NORMAL`、手动顺序回退成 0、课程名回退成空串，
  **子任务 / 周期记账 / 生活 / 学习这些段缺失时就是空列表**），
  **所以 v2~v4 的老备份也照样能恢复**——只是恢复出来的新模块是空的，这是刻意的：
  宁可少几段，也不要因为老文件里没有某个键就整个恢复失败。
  文件读写全部经由系统文件选择器（SAF）给的 `Uri`，所以既不需要存储权限也不碰网络；
  恢复走 `restore()`：一个事务里清空全部业务表（记账 / 待办 / 专注 / 子任务 / 周期记账 +
  v1.9 的 11 张新表）再整份写入，因此先弹确认框再执行。
- **多币种与取整**：币种不是另一张表，而是记在交易行上的三列——`currency`（币种代码）、
  `foreignAmountCents`（原币金额，分）、`rateScaled`（汇率，放大 10000 倍的整数，人民币自己就是 10000）。
  入库时一律折算成人民币分并存进 `amountCents`，**所以统计、预算、报表、账户分布、年度汇总全都只认
  `amountCents` 一列，不需要任何按币种分支的逻辑**。汇率用整数存是为了绕开浮点误差：
  折算时以「原币分 × 汇率 / 10000」计算，再按四舍五入取整到分（`round` 而不是截断），
  否则一笔笔累加下来余额会慢慢漂掉；`Currencies` 里预置人民币 / 美元 / 日元 / 欧元 / 港币 / 英镑六种，
  每种带自己的符号与小数位（日元没有小数），**用户填过的汇率按币种记在设置里，下次选同一个币种直接带出来**。
  外币行同时显示原币额与折算额（`$12.34 ≈ ¥87.61`），人民币行只显示一个金额，避免整页重复。
- **分类存储（`CategoryStore`）**：自定义分类存在偏好设置里，**支出、收入各存一份列表**，
  「设置 → 记账 → 分类管理」里增删，或一键写回预置分类。读的时候**空列表一律回落预置分类，
  所以这个函数永远不会返回空列表**，UI 上不会出现「一个分类都没有」的死局。
  **删分类不动历史数据**：分类名本来就直接存在 `transactions.category` 里，删除只是把名字从列表里去掉，
  已经记过的那些行原样保留、统计与筛选照旧；而记录弹窗给出的候选是
  「用户列表 ∪ 数据里实际出现过的分类」，所以被删掉的分类名只要还留在数据里就仍然能选中，
  不会出现「编辑老记录时选不回原分类」。
- **CSV 导出**：开头写 UTF-8 BOM、行尾用 CRLF、含逗号/引号/换行的单元格加引号转义，
  这样 Excel 双击打开中文不乱码，排序按日期 + id 固定。表头固定是「日期 / 类型 / 分类 / 账户 / 金额 / 备注 / 标签」
  这七列，但**文字随界面语言**：中文界面写 `日期,类型,分类,账户,金额,备注,标签`，英文界面写
  `Date,Type,Category,Account,Amount,Note,Tags`，`类型` 列的内容（支出 / 收入）也是该语言的译文；
  列数与列序在四种语言下完全一致（`I18nTest` 会替每种语言验一遍表头与数据行都是 7 列）。
  一笔的多个标签在同一个单元格里用分隔符连起来，想在 Excel 里按账户或标签对账直接筛对应列即可。
- **CSV 导入与去重指纹**：`Backup.parseCsv()` 认**自家导出的三种列数**——5 列（v1.3 时代，无账户、
  无标签）、6 列（v1.4 / v1.5，有账户无标签）、7 列（v1.6，含标签），并且**按表头文字自动识别**，
  所以四种界面语言导出的文件都能吃进来；列数与表头对不上的行不算数。
  去重靠**指纹**：一行只取「日期 + 金额 + 类型 + 分类 + 账户 + 备注」六项拼成一个字符串，
  和库里已有记录的指纹一起塞进 `Set`，命中就跳过这一行——**因此同一个文件导两遍不会多出一条**，
  而备注里写的内容不同就仍然算两笔，不会被误吞。**解析不了的行直接忽略**（不抛异常、
  不中断整次导入），最后只回报「导入多少、跳过多少」，`insertTransactions()` 批量写库，
  中途不会出现半份数据。指纹刻意不含标签与币种：这两项是后加的可选信息，
  老导出里没有，把它们算进指纹反而会让同一笔记录重复导入。
- **重复任务日期推算**：`nextDueMillisOf()` 是纯函数（可直接跑 JVM 测试）——
  每天/每周/每月顺延，顺延结果落在过去时继续往后推，不补一串过期任务；
  月末夹取用 `plusMonths` 的自然夹取（1 月 31 日的下一个月是 2 月 28 日）。
- **子任务与级联删除**：子任务是独立表（`subtasks.todoId` 指向待办），所以一条待办可以带任意多条。
  列表行只在**有子任务时**才显示 `2/5` 与细进度条（`subtaskProgress()` 没有子任务就返回 null，
  不给整页塞无意义的 0/0）。删待办时先按 `todoId` 删掉它的全部子任务再删待办本身
  （`deleteForTodo`），不留孤儿行；整库恢复时子任务表也一起清空重建。
  子任务只有标题、勾选状态与顺序，没有截止日、没有层级，也不进任何统计。
- **优先级与拖拽排序**：`TodoPriority` 是枚举（`LOW` / `NORMAL` / `HIGH` / `URGENT`，
  中文是低 / 普通 / 高 / 紧急），以字符串存在 `todos.priority`，老数据默认 `'NORMAL'`，
  所以迁移不需要回填。行上只有非普通优先级才画标记，免得整页都是徽章。
  手动顺序存在 `todos.sortOrder`：长按进入拖拽、放手时把可见列表整份交给 `reorderTodos()`
  按新下标写回，单击仍然是打开编辑（拖拽与点击由长按手势区分）。
  **搜索中、已完成筛选和看板视图下不给排**：搜索结果和看板分组都不是「整张列表」，
  重排会把看不见的行挤到别处；这时界面直接说明不支持排序，而不是默默没反应。
- **看板分组**：`TodoBucket`（`TODAY` / `THIS_WEEK` / `LATER` / `NO_DATE` / `DONE`）是纯函数式的分桶，
  `kanbanSections` 把同一批待办按到期日分进五组、每组带上条数，空组不渲染；
  搜索时不用缓存好的 `kanbanSections`（它不带搜索词），而是把过滤后的可见待办按同一套规则重新分桶，
  所以「搜索 + 看板」也能得到正确结果。分桶规则本身（已完成永远优先、今天与逾期同组、
  第 7 天归「以后」、没有到期日单独一组、每条只落进一个组）由 `TodoBucketTest` 的 6 个用例钉住。
- **周期记账的补记语义**：规则存在 `recurring_tx` 里，一行就是一条固定支出（金额 / 类型 / 分类 /
  账户 / 备注 / 标签 / 规则 / 下次到期日 / 启停）。**不跑后台服务**：应用启动时（以及每晚提醒那条路径）
  调 `materializeRecurring()`——取出 `enabled` 且 `nextDueMillis <= 今天` 的规则，在一个事务里
  各写一笔真实流水，再用纯函数 `nextDueMillisOf()` 把 `nextDueMillis` 推到未来。
  这个函数**保证算出来的日期一定在今天之后**，所以「补一次 → 推一次」不会立刻又到期，
  长期没打开也只会补出**一条**（规则里存着的那一期），而不是把中间落下的每一期都刷进账本；
  补完规则就已在未来，重复调用不会再记一遍。暂停的规则（`enabled = false`）直接跳过，恢复后继续；
  删除规则只删规则本身，已经写进账本的流水照旧保留。
- **按待办统计投入时间**：专注记录里存的是**开始专注时那个待办的标题快照**（`taskTitle`），
  统计时先滤掉空标题、再按标题分组，按时长倒序取前 10 条，所以「没有从待办发起」的普通番茄
  不会混进这张卡片。用标题快照而不是外键，是为了不动 `focus_sessions` 的表结构、也不给老数据补外键
  （v1.7 虽然给子任务建了关联表，但专注记录这一侧没有动）；
  代价是**待办改名后旧记录仍算在旧标题下**，不会跟着改。
- **待办提醒**：用 AlarmManager 的**非精确**闹钟 `setAndAllowWhileIdle`，不申请
  `SCHEDULE_EXACT_ALARM`，Android 12+ 也不用再引导用户去系统设置授权。排程是幂等的
  （先撤销上一轮再按需重排），提醒接收器到点重新查库确认还没完成才通知；
  「已提醒」以 `id:到期日` 为键存在设置里，最多打扰两次（到期日 9:00 + 次日 9:00），
  改期后键变了会重新提醒；通知带跳转 Intent，点一下直接回到应用。
  v1.5 起通知上多了「1 小时后」/「明天早上」两个动作：点下去先撤掉当前通知，再排一个延迟闹钟
  （`data` 里带上触发时刻，所以它和常规排程是两个不同的 `PendingIntent`，幂等 `sync()` 重排时不会误撤），
  到点再提醒一次；这次触发带 `snooze_fire` 标记，**不写「已提醒」记账**，
  因此稍后提醒不会吃掉正常的两档额度。
- **每晚记账提醒**：`LedgerReminder` 和待办提醒共用同一套做法（`setAndAllowWhileIdle`、
  同一个幂等 `sync()`），只是时间由设置决定（默认 21:00，可在「设置 → 记账 → 提醒时间」用
  TimePicker 改成任意时刻），`nextTriggerMillis()` 是纯函数：今天的点还没到就排今天，过了就排明天，
  因此有 4 个 JVM 用例专门覆盖它。开关或时间一变、App 启动、重启 / 覆盖安装后、以及每次提醒触发后都会重排，
  而且每次都按**当时的系统时间**重新算触发点，所以手机时间或时区被改过之后，
  最迟到下一次重排（触发一次、重启、或打开应用）就会自动回到用户设置的钟点上，不必手动关开开关。
  `LedgerReminderReceiver` 发完通知立刻排下一天，不依赖 App 常驻。
  v1.5 起这个时间点还兼任「每日专注目标」的判定：`LedgerReminderReceiver` 到点先数一遍今天的番茄数，
  没达标就补一条通知（记账提醒和专注目标各看自己的开关，谁开着做谁的事，两个都关就什么都不做）。
  这个每日闹钟**始终排着**：`LedgerReminder.sync()` 无论开关如何都会排下一次，
  两个开关都关时它固定按 21:00 干活、不发通知——因为 v1.8 起它还兼任两件事：
  ① `materializeRecurring()` 补记到期的周期记账（固定支出不能因为用户关了提醒就漏记），
  ② `AutoBackup.runBackupIfDue()` 做当天那份自动备份（没开自动备份、或还没挑文件夹时它什么都不做）。
- **定期小结**：`SummaryReminder` 复用同一套非精确闹钟做法，`nextTrigger()` 是纯函数
  （每周 → 下一个周日 20:00，每月 → 下一个 1 号 10:00；今天正好就是周日 / 1 号而点还没到，就用今天），
  `rangeFor()` 同样是纯函数（周日发的是「刚过去的周一到今天」，1 号发的是「上一个自然月」）。
  到点由 `SummaryReceiver` 现场重算这段时间的支出、收入、专注时长与次数再发一条通知，
  **完全没数据就不发**（只统计区间里有记录或专注才会打扰），且无论算不算得出来都排下一次，
  免得小结从此断掉；重启 / 覆盖安装后由 `BootReceiver` 一并重排。
- **环比对比的算法**：`Comparison` 持有六个金额（本月 / 上月的支出与收入、今年 / 去年的支出），
  三个百分比各用各的分子分母，绝不互相串。`percentOf()` 在基数为 0（或负）时**返回 null**——
  上个月一笔都没记的时候，任何百分比都是瞎话，界面据此说「两笔金额无法比较」，
  而不是显示 0% 或 +100%；基数正常时返回**带正负号的整数百分比**
  （`(now - base) / base × 100` 取整，10000 → 10333 是 +3）。月份对比跟着统计页选中的月份走
  （把月份切到上个月，比的就是上上个月），年份对比同年口径。`ComparisonTest` 的 5 个用例
  钉住的就是这几条：缺基数返回 null、带符号取整、整体归零是 −100%、三对数字各用各的。
- **月报生成**：`report/MonthlyReport.kt` 只做生成，输入一个 `MonthlyReportData` 值对象
  （当月收支、每日柱状图、分类构成、专注统计、环比与洞察文案，全部由 `MainViewModel` 算好并按当前语言拼好），
  输出三种格式：**PNG**（`Canvas` + `Bitmap` 手绘，宽 1080 起，可以直接分享）、
  **HTML**（自己拼字符串，**只用内联 CSS，不含 `<script>`、不引用任何外部资源**，
  所以离线双击就能正常阅读）、**PDF**（`android.graphics.pdf.PdfDocument`，A4 页尺寸，
  内容多了自动加页，中文按字符数粗略折行以免裁字，写完无论成败都 `close()` 释放原生页缓冲）。
  三种都写到系统文件选择器给的 `Uri`，所以仍然不需要存储权限，也没有新增任何第三方库。
  当月一条记录都没有时**不出文件**，只提示没有可导出的内容——空文件比没有文件更糟。
- **桌面快捷方式**：`res/xml/shortcuts.xml` 声明「记一笔 / 加待办 / 开始专注」三个静态快捷方式，
  各自往 `MainActivity` 塞一个 `tab` 编号；Activity 是 `launchMode="singleTop"`，
  `onCreate` 与 `onNewIntent` 都走同一个 `consumeShortcut()`，并用一个自增的 `requestSeq`
  让「连续点同一个快捷方式」也能重新切回那个标签页，而不是没反应。
- **通知跳转**：所有通知（待办提醒、每晚记账提醒、预算预警、定期小结、专注目标）都带
  `PendingIntent` 指向 `MainActivity`，点通知即可回到应用；发送前统一过一遍 `canNotify()`
  检查通知权限，没授权就安静地不发（`POST_NOTIFICATIONS` 之外的权限一律不申请）。
- **应用锁已在 v1.9 删除**：v1.8 曾经有过一个「自设 4~6 位数字密码」的应用锁
  （`security/PinCode.kt` 的密码规则 + `security/AppLockStore.kt` 的独立 prefs `dailybook_applock` +
  `ui/LockScreen.kt` 的数字键盘 + `PinCodeTest` 的 8 个用例），**v1.9 按用户要求整条移除**：
  功能、设置卡片、解锁页面、密码代码与对应测试一并删掉，`security/` 目录与 `ui/LockScreen.kt`
  在仓库里已经不存在，`ui/SettingsScreen.kt` 里那张「安全」卡片也随设置页拆分一起消失。
  所以**现在这个应用没有任何锁屏、没有任何密码、也没有指纹 / 人脸**
  （依旧不引 `androidx.biometric`，也没有 `KeyguardManager` 那条设备锁路径），
  打开就是主界面。删除的理由是它没被用上，而它带来的复杂度（上锁时机、忘记密码的出口、
  一张只服务少数人的设置卡片）一直都在。**要注意这也意味着数据完全敞开**：
  数据库、备份 JSON、CSV 都是明文，拿得到解锁的手机就能直接看——这是取舍，不是疏漏。
- **桌面小组件**：`widget/WidgetProvider.kt` 继承框架的 `AppWidgetProvider`，
  界面用 `RemoteViews` 拼（**不是 Glance**，所以一个依赖都不用加）。
  刷新有三条路：系统按 `res/xml/widget_info.xml` 里的 `updatePeriodMillis`（1800000 ms = 30 分钟，
  系统允许的最小值）唤起 `onUpdate`；App 数据一变就发一次自家广播 `ACTION_REFRESH`
  （`refresh()` 用 `setPackage()` 只投给自己，不需要任何权限，桌面上没小组件时系统直接丢掉）；
  用户把小组件拖到桌面时系统再发一次 `APPWIDGET_UPDATE`。
  数字口径和 App 内一致：今日支出 / 收入按 `amountCents` 当天汇总（外币早在入库时就折算成人民币，
  小组件不需要任何按币种分支），待办数 `!done`，专注分钟按当天会话累加。
  `onUpdate` 跑在主线程，所以查库挪到 `Dispatchers.IO` 协程里，并用 `goAsync()` +
  `finally { result.finish() }` 告诉系统「这次广播还没处理完」（和 `LedgerReminderReceiver` 同一套写法）；
  异常一律吞在接收器里——小组件里冒异常会弹 ANR 对话框。
  点击事件挂在根布局上，`PendingIntent.getActivity` 带 `FLAG_IMMUTABLE`（Android 12+ 的硬要求）
  与 `FLAG_UPDATE_CURRENT`，点哪儿都打开应用。
  文案走 `@string`：桌面上的文字跟随**系统**语言，若 App 内选的语言系统认识（中 / 日文）就用
  `createConfigurationContext()` 重取一次资源，尽量贴近 App 内所见。
  **release 有坑**：布局是代码里按名字取的（`R.layout.widget_dailybook`）、provider 配置只出现在
  manifest 的 `meta-data` 里，静态扫描不一定认得全，R8 + `shrinkResources` 一旦裁掉就是
  「debug 正常、release 一片空白」这种最难查的问题，所以 `res/raw/keep.xml` 用 `tools:keep`
  把那几个 `@layout` / `@drawable` / `@xml` 与 `@string` 显式钉住。
- **自动备份**：`backup/AutoBackup.kt` 把整份数据写成 JSON 放进**用户自己挑的文件夹**——
  用 `ActivityResultContracts.OpenDocumentTree()` 选树，然后 `takePersistableUriPermission()`
  申请持久读写授权（申请失败不算错：有的第三方文件管理器就是不支持，本次运行内照样能用，
  下次真去写时发现没权限就如实报 `NO_PERMISSION`，让用户重挑）。
  因为文件在 App 私有目录之外，**卸载重装、清数据都不会把它带走，换机直接拷走就行**——这才是自动备份的价值；
  反过来也意味着它在别的 App 或云同步盘里是明文可读的（记账和待办），所以文档里明说「介意就别挑同步盘」。
  **触发时机只有两个：App 打开时、每晚记账提醒闹钟响时**（`MainViewModel` 的启动协程与
  `LedgerReminderReceiver`），**没有任何后台任务、没有 WorkManager、没有前台服务**，
  所以长期不开 App 就不会有新备份——这是写明的已知限制，不是没做完。
  文件名叫 `DailyBook-backup-YYYYMMDD.json`（本地日期，跟用户的「今天」一致）：
  写之前先在树里找同名的，找到就**覆盖内容**，找不到才 `createDocument`，所以**一天最多一份**，
  反复开 App 不会刷出一堆 `… (1).json`；两次备份之间还有 24 小时的下限（更细的粒度没有意义）。
  轮换保留最新 **7** 份，排序键是**文件名里的 8 位日期**而不是提供方给的修改时间
  （有些提供方根本不填 `COLUMN_LAST_MODIFIED`，而且覆盖写同一天文件时修改时间会变，用文件名才稳定）；
  **只处理名字以 `DailyBook-backup-` 开头的文件**，用户在同一个文件夹里放的别的文件一律不删。
  失败处理刻意「诚实」：结果回 `BackupOutcome` 四个值（成功 / 没配置 / 还没到点 / 真失败），
  原因回 `BackupFailureCode`（没权限 / 建不了 / 写不进 / 清理失败 / 未知），
  两个都是枚举、本模块里**没有任何面向用户的句子**（文案交给设置页按当前语言查词条）。
  **失败不动「上次成功备份」的时间戳**，界面因此永远显示的是真正的上一次成功；
  失败后还有 1 小时退避，免得每次开 App 都对着一个坏文件夹猛撞；清理那一步单独 `runCatching`，
  「备份写成了、清理没成」会记成 `LIST_FAILED` 而不是假装全好。
- **日历视图与筛选**：记账页可在列表 / 日历之间切换，日历显示所选月份的每日支出，
  颜色越深表示当天花得越多（按当月最大值归一化，所以月份换了配色跟着重算）。
  点某一天就把下方列表筛成那一天的流水，**再点同一天即取消**，因此「看某天」和「看全月」
  来回只需要点两下，不用额外清空按钮。标签筛选行与账户筛选胶囊是同一套做法：

- **记账页的单面滚动（v1.9，修的是用户报上来的 bug）**：原来的日历是内容区里 `LazyColumn`
  **旁边**的一个兄弟节点，装在不可滚动的 `Column` 里；上面那几张固定高度的汇总 / 筛选卡再加一张日历
  正好占满一屏，于是列表被挤到只剩几十个像素高，手指在日历上也滚不动——现象就是「日历一打开，
  整页就滚不了了」。修法不是加内边距或者把日历压扁，而是**把日历挪进 `LazyColumn` 当第一个 item**
  （`item(key = "month-calendar")`），让整页只有**一个**滚动面：卡片、日历、流水依次排下去，
  一起滚、什么都不裁，日历也不再和列表抢高度。顺带写了一句提示文案（`calendarScrollHint`），
  说明滚动即可看完整页面。教训很直白：**一个可滚区域里只应有一个滚动容器，固定高度的兄弟节点
  拼起来很容易把后面的内容挤没**——这类问题在预览里看着正常，只有真的滚一下才会暴露。
- **年 / 月快速切换条（v1.9）**：记账页和统计页之前都只有一对 ◀ ▶，从一个远一点的月份跳回来要点十几下。

- **农历（v1.9）**：`util/Lunar.kt` 把 1900–2100 每年的农历数据压成一个 0x 整数（闰月大小 + 12 个月大小
  + 闰月是第几月），配合一个起点做加减法，就能双向换算阳历 ↔ 农历，并给出月名 / 日名与闰月标记。
  **整张表的零点是 `EPOCH_EPOCH_DAY = -25537`，也就是 1900-01-31（1900 年正月初一）**——
  这个数字看着不起眼，却是最容易写错的一处：1900-01-01 的 epochDay 是 **−25567**，
  两者差 30 天，而 1900 年正月初一偏偏就是 1 月 31 日。**零点写错，每一个农历日期都会整体偏一个月**
  （春节跑到正月三十、中秋跑到八月十四这种），而且十二个月里看着都「差一点点」，
  非常像格式化 bug，实际是表头对错了地。`LunarTest` 的 24 个用例就是钉这件事的：
  春节 / 中秋 / 端午与纪元当天的已知日期、闰月年（含闰月大小）、阳历 ↔ 农历往返、
  月名与日名，以及**闰月生日在非闰年时回退到同月同日**（过农历生日的人不能因为那年没闰月就整天算不出来）。
  超出 1900–2100 的输入按边界夹逼、不抛异常——宁可给个边界日期，也不要在「重要日期」页里崩掉。
  重要日期的 .ics 导出用的是同一份换算结果，所以导进手机日历的那一天和 App 里显示的那一天一定一致。
- **生活与学习两个模块的数据落点（v1.9）**：能复用就复用，能不建表就不建表。
  **作业 / DDL 不是一个独立模块**：它就是 `todos` 表里 `courseName` 非空的那批行，按逾期 / 今天 /
  本周 / 以后 / 没有日期 / 已完成分组渲染，所以在学习页勾掉一条作业，待办页那条也是勾上的——
  同一行数据，不是两份。**背单词 / 背书计划也不是一张表**：它就是一个带单位（页 / 个）与每日目标的
  「习惯」，打卡记录落在 `habit_logs` 里，周报里那一项就是最近 7 天 `habit_logs` 的条数。
  真正新增的只有 11 张表，而且都是「一行一条记录 + 一个 DAO」这种最朴素的形状，
  没有外键级联、没有 join——查询都在内存里按 id 分组（数据量是个人级别，足够了）。
  这样做的代价写在「已知取舍」里（周报的待办项给不出完成时间），但换来的是**不需要动
  `todos` 之外任何既有表的结构**，迁移风险最小。
- **GPA 的换算只在一个函数里（v1.9）**：`ui/study/GradesScreen.kt` 的 `scoreToPoint(score, kind, scale)`
  是唯一的换算入口，界面上只负责预览与保存。三种录入方式都可以混着录，因为**入库的 `point` 才是
  GPA 唯一认的字段**：百分制按国内最常见的 4.0 分段（90+ = 4.0、85–89 = 3.7、82–84 = 3.3、
  78–81 = 3.0、75–77 = 2.7、72–74 = 2.3、68–71 = 2.0、64–67 = 1.5、60–63 = 1.0、60 以下 = 0.0），
  五级制按 优秀 4.0 / 良好 3.0 / 中等 2.0 / 及格 1.0 / 不及格 0.0（英文 excellent / good / fair / pass / fail
  也认），直接给绩点就是填多少算多少。**设置里选 5.0 口径时不做另一套表，而是把 4.0 的结果整体
  乘 5/4**（90 分 = 5.0、85 分 = 4.625、75 分 = 3.375、60 分 = 1.25）——这样两种口径之间只差一个比例，
  不会出现「切了口径之后某些分数反而变大变小」的怪事。认不出来的输入一律返回 0.0 并提示换算不出，
  永不抛异常。
- **配色方案与对比度（v1.8 起，v1.9 扩到十二套）**：`ui/theme/Palette.kt` 里 `ThemePalette` 是十二套配色
  （青 `TEAL`（默认）/ 靛蓝 `INDIGO` / 紫罗兰 `VIOLET` / 玫红 `ROSE` / 琥珀 `AMBER` / 森林 `FOREST` /
  天蓝 `SKY` / 薄荷 `MINT` / 珊瑚 `CORAL` / 咖啡 `COFFEE` / 石墨 `GRAPHITE` / 樱花 `SAKURA`），
  每套给一组 `PaletteSpec`，再由 `lightSchemeOf()` / `darkSchemeOf()` 拼成 Material 3 的浅色 / 深色配色。
  **只换品牌色**（主色 / 主色容器 / 次色 / 第三色），而**中性底色、表面色与描边这十二套共用同一份**
  （`Color.kt` 里的 `LightBackground` / `LightSurface` / `LightSurfaceVariant` / `LightOutline` 与深色那一组）：
  这样每套配色的层次、分隔感与对比度基线完全一致，绝对不会出现「某个配色在深色下糊成一团」，
  换配色只改气氛、不改信息结构。
  选中的方案存在设置里（`SettingsStore.palette`，默认 `TEAL`），由 `DailyBookTheme(palette = …)`
  套进 `MaterialTheme`；**`dynamicColor` 打开时优先用系统取色**（`dynamicLight/DarkColorScheme`，
  Android 12+），此时用户选的配色不生效——设置页会直接说明这一点，而不是让人以为开关坏了。
  对比度不是靠看截图，而是**算出来的**：`PaletteContrastTest` 对**十二套 × 明暗两套**逐个跑
  WCAG 相对亮度公式，正文（底色上的正文）要求 **≥ 4.5:1**、
  控件与主色按钮上的文字 / 图标要求 **≥ 3:1**，
  **另有一条断言要求十二套主色互不相同**（防止某个配色写错、切了没变化）。
  深色下最容易出事的次色 / 第三色就是被这两条钉住的；**从 6 套加到 12 套之所以敢加，
  就是因为这套测试会把每一套都过一遍**——手工看十二张截图是看不过来的。
- **正计时与中断记录**：专注页有两种模式，番茄钟走倒计时，正计时只往上走、点「完成」把已经过去的
  这段时长记成一条会话；**中断记录**则发生在番茄模式里——中途停止或跳过专注阶段时，
  只要这一段已经过 1 分钟就照样入库，并给 `focus_sessions.interrupted` 置 1，
  统计页据此把这条标出来（不足 1 分钟的碎片直接丢弃，免得误触也留一条）。
  **休息阶段一律不记录**，只有专注阶段才写 `focus_sessions`。
  两种模式共用同一张表和同一套统计，所以热力图、连续天数、按待办投入时间不用区分来源。
- **计时不受重组影响**：倒计时基于 `SystemClock.elapsedRealtime()` 时间戳，
  切页面、转屏都不会走偏（正计时同理，它只是把剩余时间换成已用时间）。
  计时跑在 ViewModel 中（未用前台 Service），进程被系统杀死会中断。

  另用**真实 SQLite** 跑过「v6 老库 → 跑迁移 → v7」并逐列比对 Room 自己生成的 DDL
  （脚本 `verify-migration-v19.js`），确认结构一致、老数据不丢。
  农历那张表也用 Node 与参考实现逐项对过（`verify-lunar-table.js` / `verify-lunar-dates.js`）。
  但**界面在真机上的行为（桌面小组件在真机启动器上的排版与刷新、倒计时小组件的「切换」热区、
  课表在窄屏上的密度、农历日期在重要日期页的显示、PDF 排版、通知弹出）没验证过**，
  也没在任何真实设备上点过一遍——装机试用后如有问题需再修。
  另外「release 资源压缩」只是**用 `tools:keep` 声明**（`res/raw/keep.xml`）加静态核对，
  真机上「debug 正常、release 空白」这类问题最好还是装一次 release 包亲眼确认。
- 记账的 CSV 导出**现在也有对应的导入**：导入认本应用自己导出的 5 列 / 6 列 / 7 列三种列数与四种语言的表头，
  **不认第三方账单 App 或银行导出的表头**。去重指纹是「日期 + 金额 + 类型 + 分类 + 账户 + 备注」，
  所以**同一天同金额同分类同账户同备注的两笔真实消费只会留下第一笔**（想都留住，就得让备注或账户有区别）。
  导入只做加法：不改动已有记录，也不会去合并「看着像同一笔、但字段不一致」的行。
- 多币种是**记账那一刻的汇率快照**，不是汇率表：汇率由用户手填、只按币种记住一个值，
  **应用不联网取汇率，事后也不会用新汇率重算历史记录**；原币金额留着只为显示，
  统计一律只看折算后的人民币分。币种固定六种，也不做币种之间的直接换算——任何换算都经由人民币。
  账户只是一个名字标签，**没有账户间转账、没有账户余额**。
- 标签就是记录里的一个字符串字段（多个标签用分隔符拼起来），**没有标签管理页、没有层级、也不进统计**，
  它只出现在筛选行和导出的 CSV 里；分类管理删掉的分类名会从候选列表里消失，
  但**只要还有记录在用这个名字，它就仍会出现在记录弹窗的候选里**（见上文「分类存储」），
  所以清理完一个分类，光看列表看不出它是否还残留在老记录上。
- 分类管理只负责增删名字，**不能排序、不能重命名，也不能自定义 emoji 或颜色**——
  非预置分类只能用默认徽章；预置分类一键恢复会整份覆盖用户自己加的列表。
- 分类预算只对支出分类生效，且只按月计；它按分类名存在设置里，和分类数据不强绑定——
  把某个分类的记录全删了，预算条目依然留着，要去「设置 → 记账 → 分类预算 → 管理」里手动清掉。
- 待办提醒和每晚记账提醒都是**非精确**闹钟，9:00 / 21:00 的通知可能晚几分钟；
  待办最多自动提醒两次（到期日 9:00 + 次日 9:00），而「1 小时后 / 明天早上」两个稍后提醒
  **不计入这两次**——它们只是「再响一次」，所以用户可以一直点下去，应用不会拦；
  每晚提醒每天一条，不会判断「今天是不是已经记过了」。
- **分类名和账户名是数据，不是界面文案，因此刻意不翻译**：它们随记录一起存进数据库
  （`transactions.category` / `transactions.account`），换个语言去翻译会直接让老记录
  对不上筛选胶囊和分类预算的键。所以界面切成 English / 日本語 之后，
  记账页里看到的仍然是当初存进去的中文分类名与账户名——这是有意为之，不是漏翻。
  类似的还有 `focus_sessions.taskTitle`（专注开始时取的待办标题快照）。
- 语言只覆盖应用内的界面、通知和导出内容：启动器名称与桌面快捷方式名称属于系统 UI，
  跟随**系统**语言，在应用里切语言不会改变它们。
- 定期小结的发送时刻是写死的（每周日 20:00 / 每月 1 日 10:00），设置里只能选关闭 / 每周 / 每月，
  不能改时间；预算预警只在「记完一笔」之后判定，改预算或导入备份不会立刻触发预警。
- 桌面快捷方式只能跳到标签页，不会自动把「记一笔 / 加待办」的弹窗也一并打开。
- 从 v1.1 升级时，v1.1 若曾用 DataStore 记过专注次数，那部分历史计数不会迁移
  （v1.2 起专注统计以记录表为准）。
- **子任务、优先级和手动顺序都是「待办自己」的属性，不进统计**：子任务没有截止日、没有提醒、
  没有层级，也不会出现在「按待办统计投入时间」那张卡里（那张卡只认 `focus_sessions.taskTitle` 快照）；
  优先级只决定行上那个标记（普通不标记），**不参与任何自动排序**；手动顺序就是整张列表的下标，
  所以搜索中 / 已完成筛选 / 看板视图下不能拖——那三个场景里「可见列表」不等于整张表，
  硬排会把看不见的行挪位置，这时宁可明说。拖拽只改顺序，不改到期日、也不会顺手按优先级重排。
- **周期记账是「打开时才补」的**：没有后台服务、没有 WorkManager，补记发生在应用启动或每晚提醒那一步，
  所以手机一直不开就不会有记录落库；而且一次只补**一条**（规则里存着的那一期），
  中间落下的期数不会逐期补出来，想要完整历史得自己手动补。规则没有「结束条件」
  （不能只重复 12 次）、没有「已执行几次」的计数，也只有一个下次到期日。
- **月报一次只导出当前选中的那一个月**：点一个按钮出一个文件，没有历史月份批量导出；
  产物是**静态快照**（HTML 里只有内联 CSS，没有脚本、没有交互），生成之后再记的账不会回填进去；
  PDF 的中文折行按字符数粗略估算，长备注是折断而不是整词换行。
- **环比和洞察只跟「已经记下的数据」说话**：没有可比基数时宁可说「无法比较」，或者干脆一条都不显示，
  所以本月刚开张、上月也没数据时，这两张卡会比较安静；洞察最多 4 条，都是固定模板句，
  不能自定义、也不做预测或建议。
- **大事记与奖助里的图片只标记、不渲染**：`milestones.imageUri` 与 `awards` 的附图字段都会存下来，
  列表上也确实显示「有图」的提示，但**界面里不画那张图**——这个版本没有打包任何图片库
  （没有 Coil、没有 Glide），单独为两处配图引一个图片加载依赖不划算，用系统 API 自己写又要处理
  缩放、方向、内存与回收一整摊事。所以现在它是「占位提示」，将来要真显示，得先把这段补上。
  自定义背景图那一条是例外：它只解码**一张**、只按屏幕宽度采样一次，用 `BitmapFactory` 就够，
  不需要通用图片加载器。
- **学习周报里的「待办完成」是一个总数，不是这 7 天完成的数**：`todos` 表**没有存完成日期**
  （只有 `done` 布尔值与创建时间），所以周报只能给 `todos.count { it.done }`——**目前已完成的总条数**，
  它不会随周数变化。页面上也照这个口径写，而不是假装它是「本周完成 N 条」。
  要变成真的「本周完成」，得给 `todos` 加一列 `doneAtMillis` 并再走一次迁移，本版没做。
- **统计的详情页跟着「当前选中的月份」走**：本月记录 / 分类明细 / 每日明细 / 专注记录 / 待办完成情况
  这五页用的都是统计页那个 `YearMonth`，**没有自己的时间选择器**。所以从详情页看到的数字
  一定和统计页一致（这是有意的：两处口径不一致更糟），但如果你想「在详情页里单独看某个月」，
  得先回统计页（或记账页）用年 / 月快速切换条把月份切过去。专注记录页同理——它按选中月份过滤，
  不是按「最近」。
- **两个小组件都只报很窄的一片**：今日小组件是今日支出 / 收入 / 未完成待办 / 今日专注分钟四项，
  **没有本月汇总、没有预算进度、没有热力图**；倒计时小组件一次只显示**一场**考试
  （名称 / 日期 / 倒计时 / 课程 / 地点），点「切换」才换下一场，也没有「所有考试一览」这种视图。
  两个都不做交互（没有勾选待办、没有快速记一笔、没有改考试日期的入口），点整块只会打开 App。
  数字口径跟随 App 内的当天口径，**但不会实时变**：除了 App 内数据变化时主动推一次，
  其余靠系统 30 分钟唤起一次，所以「在别的地方改了数据」或者长时间不用时，
  桌面上的数字可能滞后最多半小时；系统本身也可能因为省电策略把 `updatePeriodMillis` 的唤起往后拖。
  今日小组件的多个实例共用同一份数据与同一个点击行为；桌面上拿不到 App 主题，
  所以它的配色是写死的（深色圆角底 + 白字，`res/drawable/widget_background.xml` 的实色），
  **不跟随十二套配色**——文字跟随系统语言，只有系统认识 App 内选的语言时才贴近 App 内所见。
  倒计时小组件的「切换」位置是按实例记的（`AppWidgetManager` 的 per-widget 偏好），
  但删除小组件后那个记录不会主动清理——只是几个字节的浪费，不影响功能。
- **自动备份只在两个时刻发生**：打开 App，或每晚提醒闹钟响时。**没有 WorkManager、没有后台服务、
  没有「定时备份」开关**，所以**一直不打开 App 的人不会有新的备份**——这是明确的取舍，
  真要做到「不开 App 也备份」就得引 WorkManager 并多一个后台约束，本版故意不引。
  同一次触发里一天最多一份（同一天覆盖），加上 24 小时下限，所以「一天备份好几次」不可能；
  失败后还有 1 小时退避，短时间连开 App 不会连续重试。
  **备份文件是明文 JSON**，放在用户自己挑的文件夹里（可能是云同步盘），里面是记账、待办、
  生活与学习的全部内容——v1.9 起应用锁也没了，所以这份 JSON 唯一的门槛就是文件系统权限，
  介意的话别挑同步盘，应用不会替它加密，也没有密码保护。轮换保留最新 7 份、
  只删 `DailyBook-backup-` 前缀的文件，所以**同名规则之外的旧备份不会被清理**，
  手工复制的备份也不在轮换范围内。恢复仍然只能走「备份与恢复」里手动挑文件那一条路，
  自动备份不会自动写回数据库。
- **没有任何真机验证**：这一版是在没有连接安卓设备的构建机上做完的，上面的「已通过」都指静态验证
  （单元测试全绿、lint 0 error、release / debug 都能打出来、迁移与农历表另外用 SQLite 与 Node 对过）。
  **界面一次都没在真机上点过**，所以下面这些都得装机之后才能确认：小组件在真机启动器上的排版与刷新、
  倒计时小组件的「切换」热区好不好按、课表 7 × 12 在窄屏上会不会太挤、自定义背景图在大图上的内存表现、
  重要日期页的农历显示、日期选择器与 TimePicker 的手感、通知弹出、PDF 排版。
  发现问题的正常做法是照旧修一版，而不是当作「文档写错了」。
- **十二套配色只换品牌色**：中性底色、表面色与描边是**十二套共用同一份**（`Color.kt`），
  所以换配色不会改变界面层次，也不会换字体或圆角；**没有自定义取色器、没有按页面单独设色**，
  只有这十二个选项。
  跟随系统取色（Android 12+）打开时会盖掉所选配色，配色胶囊仍在但不起作用（设置页有说明）；
  对比度是**按配色取值算出来的**（`PaletteContrastTest` 跑 WCAG 相对亮度，十二套 × 明暗两套），
  但那只保证「文字与背景、图标与底色」达到阈值，**不保证用户自己放大字体、开高对比度无障碍设置、
  开自定义背景图蒙版拉到很淡、或换成第三方壁纸时的观感**——那些要在真机上再看。
